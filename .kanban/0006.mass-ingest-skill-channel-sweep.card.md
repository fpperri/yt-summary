# Mass-ingest skill: channel/playlist sweep over a subscription manifest

When I maintain a list of channels, I want a sweep skill that polls each for new uploads and ingests only what is missing, so mass ingestion is one command instead of per-video babysitting.

Inspiration: `~/source/fpp/.cortex/tools/skills/ingest-video/scripts/channel_videos.py` plus the sweep procedure documented in the cortex subscriptions manifest. Bake in the hard-won gotchas: RSS feeds cap at ~15 items (deep-walk /videos + /shorts, per-video upload_date gap-fill for burst channels), dedupe by channel URL and by existing slug folders, premieres fail until aired, slug collisions overwrite — skip known re-uploads.

Privacy boundary decided 2026-09-01: the manifest is an ARGUMENT the user points at (documented format, example with fake channels) — the real subscription list is personal data and lives outside the repo, never committed. Ship a `.gitignore` guard for the default manifest location.

## Acceptance Criteria
- Sweep skill reads a manifest file path, polls channels since N days, ingests missing videos via the ingest skill (#4).
- Repo contains only a documented example manifest; real manifests are ignored by git.
- Resumable and idempotent: re-running a sweep ingests nothing already present.

## Narrative
- 2026-09-01: **Sweep shipped with the listed gotchas baked in.** `scripts/sweep.py` plus `scripts/channel_videos.py`, committed `ac640da`. RSS's ~15-entry cap is handled by walking both `/videos` and `/shorts` and dating anything RSS missed per-video, bounded by a stop-after-old walk so a decade-old channel costs a handful of probes rather than one per video. Channels dedupe by normalised URL, videos by id; premieres are skipped rather than failed; rate limits back off exponentially and retry the same id. (by @assistant)
- 2026-09-01: **Privacy boundary honored.** The manifest is an argument, `examples/channels.example.txt` ships fictional channels, and `channels.txt`/`subscriptions.txt` are gitignored so the obvious working paths are safe by default. (by @assistant)
- 2026-09-01: **Idempotency proven on live data, not just in tests.** A real dry-run reported `4 candidates, 0 already ingested`; after ingesting one of them the same command reported `4 candidates, 1 already ingested, 3 to fetch`. (by @assistant)
- 2026-09-01: **Code review caught that shorts were never actually reachable.** `list_channel` merges `/videos` then `/shorts`, and the date window walked that single merged list with one early-stop counter — every established channel has more than `stop_after_old` old uploads at the tail of `/videos`, so the walk always broke before reaching the first short. The "shorts are included" line in this card, the skill and the example manifest was therefore false as shipped. The window now stops per tab. The existing tests missed it because they covered `list_channel` and `apply_date_window` separately but never composed; a composed regression test now exists. Fixed in `db5d0c4`. (by @assistant)
- 2026-09-01: **Sweep could stall for hours on one dead video, and lie about it afterwards.** The rate-limit regex matched a bare `429` against a message that embeds the video id — ids are 11 chars of `[A-Za-z0-9_-]`, so one containing `429` turned a permanently unfetchable video into a false rate-limit verdict and retried it on escalating backoff up to `--max-block`. Separately, giving up rate-limited never incremented `failed`, so the run exited `0` and a scheduled wrapper could not tell "IP blocked, nothing done" from "nothing new". Matching is now on explicit phrasing and a blocked run exits `2`. (by @assistant)
- 2026-09-01: **Polling phase was unpaced.** Per-video date probing fired back-to-back with no delay — and every video on a channel gets probed whenever its RSS lookup fails — so the polling phase could provoke the exact rate limit the ingest phase is engineered to survive. Probes are now paced, and an RSS miss is logged rather than silently swallowed. (by @assistant)
- 2026-09-01: **Handle-vs-display-name trap found the hard way.** A first live run 404'd because the channel's display name is not its `@handle`. `list_channel` now surfaces yt-dlp's own error when every tab fails instead of returning an empty list, and both the skill and the example manifest warn about it. A `/shorts` tab that 404s for a channel with no shorts is still treated as normal. (by @assistant)
- 2026-09-29: **Sweep hardened by four more review rounds.** 20 unpushed commits on `pr/ingest-digest-sweep`. Exit `2` now means rate limiting cut the run short. Polling stops at the first rate-limited channel. A throttled date probe keeps the videos RSS already dated. The listing is capped per tab, with `CAP-HIT` when the cap may hide videos. (by @assistant)
